## Record and verify delivery fingerprints

The v4.7 inventory verifies the exact set of IDs. It does not distinguish a different, internally consistent generation that reuses the same IDs. The v4.8 inventory also records one SHA-256 per delivered project, binding its ID, delivery status and sorted artifact entries (name, byte count and content SHA-256).

1. After taking a matched backup, work on the stopped snapshot or its isolated stopped copy. Record the inventory to a **new path outside the backup tree**. Store it independently with the backup's identity so the restore cannot replace its own reference.

```bash
PYTHONPATH=. python scripts/verify-artifact-generation.py --clone-root /path/to/stopped-backup --record-inventory /independent/path/delivery-inventory.json
```

2. Verify the stopped restore clone with that same reference. The verifier checks SQLite integrity, on-disk artifact bytes, exact membership and project fingerprints. A missing, extra or differently versioned delivery produces a nonzero result.

```bash
PYTHONPATH=. python scripts/verify-artifact-generation.py --clone-root /path/to/stopped-restore --inventory-file /independent/path/delivery-inventory.json
```

```powershell
.\scripts\verify-windows-restore-clone.ps1 -CloneRoot 'C:\wfs-test-restore' -InventoryFile 'D:\test-backups\delivery-inventory.json'
```

The file modes are optional and mutually exclusive with ID-list modes. Existing subset and exact-ID workflows are unchanged. A successful result does not authenticate or sign the inventory, verify unrelated application data, or certify Windows startup. The immutable reference is an operational responsibility. Do not use a reference generated by the candidate clone itself.
